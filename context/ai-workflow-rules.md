# AI Workflow Rules

## Approach

Build Gym AI incrementally with a spec-driven workflow. The context files say what to build (`project-overview.md`), how the system is shaped (`architecture.md`), how code and UI should look (`code-standards.md`, `ui-context.md`), and where the project stands (`progress-tracker.md`). Each unit of work is one spec in `context/feature-specs/`. Implement against the spec; don't infer or invent behavior.

## Scoping Rules

- One feature spec at a time, in the order of the Roadmap in `progress-tracker.md`.
- Prefer small, verifiable increments over large speculative changes.
- Don't combine unrelated system boundaries in one step.

## When To Split Work

Split a step if it combines:

- UI work and new Server Actions (unless the spec is an explicit "wire" spec). Reading data in a page is fine.
- Prisma schema changes and UI changes
- The OpenAI integration and anything else
- Behavior that isn't defined in the context files

If a change can't be verified end to end quickly, the scope is too broad. Split it.

## Handling Missing Requirements

- Don't invent product behavior (game rules, stats, AI inputs) that isn't in the context files.
- If a requirement is ambiguous, resolve it in the relevant context file before implementing.
- If a requirement is missing, add it to Open Questions in `progress-tracker.md` and don't build that part yet.
- Open Questions are answered by the user. An agent implements the defaults written in the spec.

## Protected Files

Don't modify these unless a spec says so:

- `components/ui/*` — shadcn-generated components. Style them from app components through `className`.
- `AGENTS.md` — regenerated by `next dev`.
- Applied migrations in `prisma/migrations/` — create a new migration instead.
- Existing exercise IDs in `lib/catalog.ts` — the list is append-only.

## Writing The Next Spec

Specs after 08 are written one at a time, after the previous unit is done, using `feature-specs/_templates/generate-spec-prompt.md` and `feature-specs/_templates/spec-template.md`. That way each spec matches the code as it was actually built.

## Testing On A Phone

- Checks marked **(phone)** are done by the user on a real device.
- Wake Lock and the install prompt need HTTPS. Use the Vercel preview URL (connect the repo to Vercel once the shell exists) or a tunnel such as `cloudflared`.
- To open the dev server over the LAN instead, add the machine's IP to `allowedDevOrigins` in `next.config.ts` (Next 16 blocks other dev origins by default).
- When a spec adds env vars, add them to Vercel too. From spec 08 on, deployments run `prisma migrate deploy`.

## Keeping Docs In Sync

Update the matching context file when the implementation changes:

- architecture or boundaries → `architecture.md`
- schema or storage decisions → `architecture.md` and Architecture Decisions in the tracker
- conventions → `code-standards.md`
- tokens or visuals → `ui-context.md`
- scope or game rules → `project-overview.md`

The tracker describes what is actually built, not what was intended.

## Before Moving To The Next Unit

1. The unit works end to end within its scope. UI units are checked in a 360 × 640 viewport.
2. No invariant from `architecture.md` was violated.
3. Every item in the spec's "Check When Done" passes. (phone) items are confirmed by the user.
4. `npm run lint` and `npm run build` pass, and `npm test` passes once tests exist.
5. `progress-tracker.md` is updated.
6. The unit is committed on its own (one commit per spec). The project must be a git repository; if it isn't, run `git init` and commit the current state before the first unit.
